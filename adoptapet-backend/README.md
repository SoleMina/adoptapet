# AdoptaPet — microservices backend

Spring Boot 4 · Spring Cloud (Eureka + Gateway) · Spring Security with JWT · MySQL · RabbitMQ · Java 21.

## Architecture

| Module | Port | Database | Responsibility |
|---|---|---|---|
| discovery-server | 8761 | – | Eureka registry |
| api-gateway | 8080 | – | Single entry point, routes `/api/**` by service name |
| user-service | 8081 | `pets_users` | Register, login (issues the JWT), users, workers, activate/deactivate |
| pet-service | 8082 | `pets_catalog` | Pet catalog and photos |
| adoption-service | 8083 | `pets_adoptions` | Applications, delivery slots, documents, adoption act, adopters summary, report |
| notification-service | 8084 | `pets_notifications` | In-app notifications for adopters |
| platform-common | – | – | Shared `JwtFilter`, `JwtService`, error handling and RabbitMQ event contract |

* **Tables are generated by Hibernate** from the `@Entity` classes (`ddl-auto=update`) and every database is
  created on first start (`createDatabaseIfNotExist=true`). There are no SQL scripts.
* **Security** follows the DAWII style: user-service signs an HS512 JWT (`id`, `role`, `sub`=username) and every
  service validates it with the same `jwt.secret` through `JwtFilter`. Roles: `ADMIN`, `WORKER`, `ADOPTER`.
* **Service calls**: adoption-service reads pets and users over HTTP (`http://pet-service`, `http://user-service`
  resolved by Eureka), forwarding the caller's token.
* **RabbitMQ**: adoption-service publishes an `AdoptionEvent` to the topic exchange `adoptapet.events`
  (`application.created|approved|rejected|no_show|rescheduled|cancelled|completed`) after each commit.
  pet-service updates the pet status (RESERVED / ADOPTED / AVAILABLE) and notification-service notifies the adopter.

## Requirements

* Java 21+, Maven 3.9+
* MySQL 8+ running on `localhost:3306` (defaults: user `root`, empty password)
* RabbitMQ on `localhost:5672` (`brew install rabbitmq && brew services start rabbitmq`)

## Run locally

```sh
mvn clean package -DskipTests

java -jar discovery-server/target/discovery-server-0.1.0-SNAPSHOT.jar      # start first
java -jar user-service/target/user-service-0.1.0-SNAPSHOT.jar
java -jar pet-service/target/pet-service-0.1.0-SNAPSHOT.jar
java -jar adoption-service/target/adoption-service-0.1.0-SNAPSHOT.jar
java -jar notification-service/target/notification-service-0.1.0-SNAPSHOT.jar
java -jar api-gateway/target/api-gateway-0.1.0-SNAPSHOT.jar
```

Give Eureka ~30 seconds after startup before calling through the gateway. On first start user-service creates the
admin `admin` / `Admin12345` (change it with `ADMIN_PASSWORD`).

Useful environment variables: `DB_USER`, `DB_PASSWORD`, `JWT_SECRET` (must be the same in every service),
`RABBITMQ_HOST`, `RABBITMQ_USER`, `RABBITMQ_PASSWORD`, `EUREKA_URL`, `EUREKA_ENABLED=false` (run user/pet/notification alone).

## API (through the gateway, http://localhost:8080)

| Method | Path | Access |
|---|---|---|
| POST | `/api/auth/register`, `/api/auth/login` | public |
| GET/PUT | `/api/users/me` | authenticated |
| GET | `/api/users?role=ADOPTER` · `/api/users/{id}` | staff (or self) |
| POST | `/api/users/workers` · PUT `/api/users/{id}` · `/{id}/activate` · `/{id}/deactivate` | ADMIN |
| GET | `/api/pets?status=&species=` · `/api/pets/{id}` · `/api/pets/images/{file}` | public |
| POST/PUT | `/api/pets` · `/api/pets/{id}` (multipart + `image`) · DELETE `/api/pets/{id}?version=` · PUT `/{id}/activate` | staff |
| POST | `/api/applications` (multipart + `dniFile`, `addressProofFile`) | ADOPTER |
| GET | `/api/applications/me` · `/api/applications/{id}` · `/{id}/documents/{DNI\|ADDRESS_PROOF\|ACT\|SIGNED_ACT}` | owner or staff |
| GET | `/api/applications?status=` · `/api/applications/adopter/{id}` | staff |
| PUT | `/{id}/approve` · `/{id}/reschedule` (schedule body) · `/{id}/reject` · `/{id}/cancel` (reason body) · `/{id}/no-show` · `/{id}/complete` | staff |
| POST | `/{id}/act` (returns PDF) · `/{id}/signed-act` (multipart `file`) | staff |
| PUT | `/{id}/complete-contingency` | ADMIN |
| GET | `/api/delivery-slots?date=YYYY-MM-DD` | authenticated |
| GET | `/api/adopters` · `/api/adopters/{id}` | staff |
| GET | `/api/reports/general?applicationStatus=&petStatus=&species=` (PDF) | ADMIN |
| GET | `/api/notifications/me` · `/me/unread-count` · PUT `/{id}/read` · `/me/read-all` | authenticated |

Schedule body: `{"deliveryDate":"2026-10-05","startTime":"10:00","endTime":"12:00","pickupDeadline":"2026-10-05T12:30","observation":"..."}`
(windows 10:00-12:00, 14:00-16:00, 16:00-18:00, max 2 deliveries each, Peru time). Reason body: `{"reason":"..."}`.

## Adoption workflow

```
PENDING --approve--> APPROVED --(act + signed act)--> COMPLETED
   |                    |  \--no-show--> NO_SHOW --reschedule--> APPROVED   (max 2 reschedules, then ADMIN only)
   +--reject--> REJECTED \--------cancel (APPROVED | NO_SHOW)--> CANCELLED
```

Approving one application rejects the other pending ones for the same pet. Only a HEALTHY pet can be adopted.
